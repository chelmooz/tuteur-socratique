Construire un Second Brain interactif avec Obsidian et l’IA

Ce cours transforme le transcript en parcours pratique : comprendre pourquoi un simple “dépôt de notes” ne suffit pas, puis construire un système vivant composé d’un wiki, d’un CRM, d’un journal, de fichiers sources, de pages générées, d’automatisations et de sauvegardes.

1. Le problème des second brains “décharge”

Beaucoup de systèmes de gestion des connaissances ne font que stocker : articles, transcripts YouTube, podcasts, tweets, notes. Le problème est que l’information “va mourir” dans le dépôt si rien ne la rend réutilisable.

Symptômes d’un dépôt mort

  • Vous enregistrez beaucoup, vous relisez peu.
  • Les notes ne sont pas reliées entre elles.
  • Vous ne retrouvez pas l’information au bon moment.
  • Le système devient une archéologie personnelle.

Objectif d’un second brain utile

  • Capturer facilement.
  • Traiter automatiquement ou semi-automatiquement.
  • Extraire entités, concepts, outils, personnes, idées.
  • Relier les notes entre elles.
  • Interroger la base comme un partenaire de réflexion.

2. Les 3 piliers : Wiki, CRM, Journal

Le transcript propose une architecture en trois couches : une base de connaissances type wiki, un CRM pour les personnes, et un journal pour réfléchir avec l’IA à partir de vos propres contenus.

1. Wiki / Knowledge base

Contient tout ce que vous trouvez en ligne : articles, transcripts YouTube, podcasts, tweets, notes de recherche, PDF, etc.

2. CRM

Contient les personnes rencontrées, les événements, les conversations, les coordonnées, les contextes et les relations.

3. Journal

Contient vos réflexions du moment. L’IA peut y répondre en s’appuyant sur votre wiki, vos anciens journaux et votre CRM.

Pourquoi cette combinaison est puissante

Un journal classique vous aide à réfléchir. Un journal connecté à votre base de connaissances devient un partenaire personnalisé : il peut se souvenir de ce que vous avez sauvegardé, repérer des patterns et reformuler des conseils ancrés dans vos propres centres d’intérêt.

3. Architecture Obsidian : raw, wiki, agents.md, index.md, log.md

Le transcript s’appuie sur Obsidian comme front-end de lecture et d’organisation de fichiers Markdown. L’idée est de séparer clairement les sources brutes, les pages générées, les règles de l’agent, l’index et le journal des modifications.

Rôle des fichiers clés

Élément Rôle Analogie
/raw Dossier des sources brutes et immuables. La bibliothèque originale.
/raw/processed Sources déjà traitées, pour éviter les doublons. Le tiroir “déjà lu et digéré”.
/wiki Pages Markdown générées par l’IA à partir des sources. Le manuel synthétisé.
agents.md Instructions opératoires de l’agent. Le mode d’emploi du cerveau.
index.md Catalogue des pages, entrées ou contacts. La table des matières.
log.md Journal des actions, ajouts et mises à jour. Le registre d’activité.

Prompt de démarrage pour construire l’architecture

Dans le dossier actuel, crée une architecture de second brain inspirée d’un wiki LLM : - dossier /raw pour les sources brutes, - dossier /raw/processed pour les sources déjà traitées, - dossier /wiki pour les pages générées, - fichier agents.md avec les opérations d’ingestion, de requête, de journal et de CRM, - fichier index.md comme catalogue, - fichier log.md pour tracer les modifications. Commence minimal, puis explique-moi chaque fichier avant d’ajouter des complexités.

4. Capturer avec Obsidian Web Clipper

La capture doit être frictionless : un clic depuis le navigateur envoie l’article, la vidéo YouTube ou la page web dans le dossier /raw sous forme de fichier Markdown.

Éléments à configurer

  • Nom exact du vault Obsidian.
  • Dossier de destination : raw.
  • Propriétés : titre, URL, date, tags.
  • Contenu : corps de l’article ou transcript.
  • Pour YouTube : vérifier que le transcript est bien récupéré.

Piège fréquent

Le clipper peut ne pas récupérer automatiquement certaines métadonnées, par exemple le nom de la chaîne YouTube. Il faut alors ajouter une instruction dans agents.md ou dans le prompt de traitement.

Exemple de règle à ajouter

Pour les vidéos YouTube capturées avec Obsidian Web Clipper : - récupérer le transcript dans /raw, - extraire le nom de la chaîne depuis l’URL ou la page source, - ajouter ce champ dans le front matter du fichier source, - ne pas supprimer le fichier original.

5. Traiter les sources : résumer, extraire, relier

Le traitement est l’étape qui transforme une source brute en connaissance utile. L’IA peut résumer, extraire des entités, créer des pages wiki, relier les notes entre elles et mettre à jour l’index.

Bonnes pratiques de traitement

  • Garder la source originale intacte.
  • Créer ou mettre à jour des pages concepts/outils/personnes.
  • Ajouter des liens wiki entre notes liées.
  • Mettre à jour index.md et log.md.
  • Déplacer la source traitée vers /raw/processed.

À éviter

  • Écraser la source brute.
  • Créer 50 fichiers inutiles dès le départ.
  • Oublier de relier les pages générées à leur source.
  • Tout mélanger dans un seul dossier monolithique.

Prompt de traitement

Traite les fichiers non traités situés dans /raw. Pour chaque source : 1. LIS le fichier original sans le modifier. 2. RÉSUME les idées principales en bullets. 3. EXTRACT les entités utiles : personnes, entreprises, outils, concepts, thèmes. 4. CRÉE ou METS À JOUR des pages dans /wiki. 5. LIEN chaque page générée vers la source originale. 6. METS À JOUR index.md et log.md. 7. DÉPLACE le fichier source traité vers /raw/processed.

6. Interroger le wiki : faire grandir la base par les questions

Un bon second brain ne se contente pas de répondre. Il peut aussi enrichir la base à partir des questions posées. Chaque requête devient une occasion de créer ou d’améliorer une page réutilisable.

Exemple de question

Quels conseils ai-je déjà sauvegardés pour rester motivé quand je dois faire une tâche difficile ? Réponds à partir du wiki, cite les sources, puis crée une page réutilisable si elle n’existe pas.

Résultat attendu

  • L’agent consulte index.md.
  • Il retrouve les pages pertinentes.
  • Il synthétise une réponse ancrée.
  • Il met à jour log.md.
  • Il peut créer une page “motivation pour tâches difficiles”.

Point important

Une requête n’est pas seulement une consultation. Dans un système bien conçu, elle peut aussi alimenter la base. C’est ce qui rend le wiki “composable” et vivant.

7. Journal ancré : réfléchir avec ses propres connaissances

Le journal est la couche d’interaction personnelle. Au lieu de recevoir une réponse générique, vous obtenez une réponse fondée sur votre wiki, vos anciens journaux et éventuellement votre CRM.

Ce que le journal peut faire

  • Sauvegarder l’entrée dans /journal.
  • Mettre à jour l’index du journal.
  • Chercher des pages wiki pertinentes.
  • Repérer des patterns dans vos anciennes entrées.
  • Répondre avec des conseils ancrés dans vos contenus.

Exemple de cas

Vous écrivez : “J’hésite entre titres clickbait et titres littéraux.” L’agent peut retrouver des vidéos sauvegardées sur la stratégie créateur, vos anciennes frustrations, et proposer une réponse nuancée.

Template de prompt journal

Traite le message suivant comme une entrée de journal. 1. Crée un fichier Markdown dans /journal avec date + titre court. 2. Mets à jour /journal/index.md. 3. Ajoute une entrée dans log.md. 4. Consulte le wiki, les anciens journaux et le CRM si pertinent. 5. Réponds-moi avec des insights, tactiques et questions utiles, ancrés dans mes propres contenus. 6. Signale si une information semble manquer ou contradictoire. Entrée du journal : [coller ici]

8. CRM personnel : relier personnes, conversations et idées

Le CRM n’est pas seulement un carnet d’adresses. Dans ce système, il devient une couche relationnelle : qui avez-vous rencontré, où, de quoi avez-vous parlé, quels liens avec vos projets, idées ou contenus ?

Champs utiles

  • Nom complet.
  • Comment vous vous êtes rencontrés.
  • Où et quand.
  • Coordonnées si pertinent.
  • Sujets discutés.
  • Liens vers projets/idées/pages wiki.
  • Prochaines actions.

Exemple d’usage

Avant une conférence, vous demandez : “Qui vais-je revoir ? De quoi avons-nous parlé la dernière fois ? Quels projets en commun ?” Le CRM peut répondre à partir de vos notes.

Template CRM

Ajoute ou mets à jour la fiche CRM de [Nom de la personne]. Inclus : - comment nous nous sommes rencontrés, - où et quand, - coordonnées si fournies, - sujets discutés, - liens avec projets/idées/pages wiki, - prochaines actions. Mets à jour /crm/index.md et log.md. Ne crée pas de fiche vide si aucune information pertinente n’est disponible.

9. Automatiser et sauvegarder : faire tourner le système en continu

Le transcript montre qu’on peut automatiser le traitement des fichiers /raw à intervalle régulier, puis pousser les changements vers un dépôt GitHub privé pour sauvegarder l’ensemble.

Workflow automatisé type

Une automatisation se déclenche à intervalle régulier.
Elle vérifie s’il y a des fichiers non traités dans /raw.
Si oui, elle lance le traitement selon agents.md.
Elle met à jour /wiki, index.md, log.md.
Elle déplace les sources traitées vers /raw/processed.
Elle commit et push vers un dépôt GitHub privé.

Avantages

  • Le système s’enrichit tout seul.
  • Vous capturez sans penser au traitement.
  • Les sauvegardes deviennent régulières.
  • Moins de risque d’oubli.

Précautions

  • Ne pas donner accès à tout le disque sans nécessité.
  • Vérifier les permissions en écriture/suppression.
  • Tester d’abord manuellement avant d’automatiser.
  • Utiliser un dépôt privé pour les données personnelles.

Prompt d’automatisation

Crée une automatisation qui, toutes les heures : 1. Vérifie s’il y a des fichiers non traités dans /raw. 2. Si oui, les traite selon les règles de agents.md. 3. Met à jour /wiki, index.md et log.md. 4. Déplace les sources traitées vers /raw/processed. 5. Commit et push la version courante vers le dépôt GitHub privé sur la branche main. Utilise le modèle de raisonnement le plus robuste disponible.

10. Limites, sécurité et bonnes pratiques

Un second brain augmenté est puissant, mais il manipule des informations personnelles, des conversations, des données sensibles et des sources parfois peu fiables. Il faut donc concevoir le système avec prudence.

Risques principaux

  • Sources web inexactes ou obsolètes.
  • Hallucinations de l’IA lors de la synthèse.
  • Données personnelles exposées.
  • Automatisations trop larges sur le disque.
  • Perte de fichiers si suppression mal gérée.

Bonnes pratiques

  • Toujours conserver la source originale.
  • Vérifier les affirmations importantes.
  • Limiter les permissions des agents.
  • Utiliser des dépôts privés.
  • Tester manuellement avant d’automatiser.
  • Relire régulièrement log.md.

Checklist de sécurité

  • Est-ce que l’agent a accès uniquement au dossier nécessaire ?
  • Est-ce qu’il peut supprimer des fichiers ? Si oui, ai-je une sauvegarde ?
  • Est-ce que les données sensibles sont réellement nécessaires ?
  • Est-ce que les sources citées sont fiables ?
  • Est-ce que je peux retrouver la source originale derrière chaque page wiki ?
  • Est-ce que le backup GitHub est privé et à jour ?
