Cours — Ingénierie des agents IA

Le prompt engineer n'existe plus. Voici qui prend sa place.

Poste : Prompt Engineer
Compétences requises : systèmes distribués, API design, MLOps, sécurité, gestion produit
= 5 personnes

Cette offre d'emploi n'a pas tort. Elle est juste mal nommée.

Construire des agents qui fonctionnent réellement en production, ce n'est pas écrire de meilleures phrases. C'est concevoir des systèmes.

Il y a deux ans, « prompt engineer » voulait dire : rédiger de bonnes instructions pour un modèle. Mais un agent ne se contente plus de répondre. Il réserve des vols, traite des remboursements, interroge des bases de données, prend des décisions. Quand on construit quelque chose qui agit réellement dans le monde, bien écrire un prompt devient le strict minimum.

La recette

N'importe qui peut suivre une recette. C'est le prompt engineering : le point de départ, pas la maîtrise.

Le chef

Le chef comprend les ingrédients, les techniques, le minutage, le flux de la cuisine, la sécurité — et sait improviser quand ça déraille. C'est l'agent engineering.

Sept compétences séparent la recette du métier de chef. Certaines, tu les as déjà.

01

Conception système

Un agent n'est pas un bloc unique. C'est un orchestre : un LLM qui décide, des outils qui exécutent, une base qui garde l'état, parfois des sous-agents spécialisés.

Trait plein = appel synchrone · trait pointillé = état persistant

C'est de l'architecture : comment les données circulent, ce qui se passe quand un composant tombe, comment coordonner une tâche qui traverse trois spécialistes différents.

Repère Si tu as déjà conçu un back-end avec plusieurs services qui se parlent, tu connais déjà ce langage. Sinon, c'est le premier chantier : un agent reste un logiciel, et un logiciel a besoin de structure.
02

Contrats d'outils

Chaque outil est un contrat : « donne-moi ces entrées, je te rends cette sortie ». Un contrat vague se fait combler par l'imagination du modèle — et l'imagination n'a rien à faire dans une transaction financière.

Schéma flou

{ "user_id": "string" }
"John" "user_123" "???"

Schéma strict

{
  "user_id": {
    "pattern": "^usr_[0-9]+$",
    "required": true
  }
}
usr_482917 ✓
Repère Un schéma qui dit juste « une chaîne » laisse la porte ouverte à tout. Un pattern précis, un champ requis, un exemple concret : le modèle sait exactement quoi faire. C'est le correctif à plus fort effet de levier sur la plupart des agents.
03

Ingénierie de la récupération (RAG)

Plutôt que de compter sur ce que le modèle a mémorisé, on va chercher des documents pertinents et on les injecte dans le contexte. La qualité de ce qui est récupéré fixe le plafond de performance de l'agent.

Flux de récupération

Trois curseurs comptent : la taille des chunks (trop gros dilue les détails, trop petit perd le contexte), la qualité des embeddings (les concepts proches doivent atterrir proches), et le re-ranking, une seconde passe qui remonte les résultats vraiment pertinents.

Repère Si tu nourris l'agent avec des documents hors-sujet, il répondra avec assurance en s'appuyant sur du hors-sujet — il ne sait pas que le contexte est mauvais, il fait juste avec ce qu'on lui donne.
04

Ingénierie de la fiabilité

Les agents appellent des API. Les API tombent en panne. Sans garde-fous, un agent peut attendre indéfiniment une réponse qui ne viendra jamais, ou retenter la même requête à l'infini.

Retry avec délai croissant → circuit breaker → repli

Retry avec backoff pour ne pas marteler un service en panne. Timeout pour ne jamais rester bloqué. Chemins de repli quand le plan A échoue. Circuit breaker pour empêcher une panne locale de tout faire tomber.

Repère Si tu as de l'expérience back-end, tu connais déjà ce playbook. Sinon, c'est la partie que la plupart des builders d'agents apprennent à leurs dépens, en production.
05

Sécurité et sûreté

Un agent est une surface d'attaque. Une injection de prompt tente de glisser des instructions malveillantes dans une entrée utilisateur pour écraser ta consigne système.

Une injection bloquée avant d'atteindre l'agent

Au-delà des attaques, il y a l'hygiène de base : l'agent a-t-il vraiment besoin d'un accès en écriture à cette base ? Peut-il envoyer des e-mails sans validation ?

Repère Validation des entrées, filtres de sortie, périmètres de permission. Même mentalité que la sécurité applicative classique, appliquée à un nouveau type de système.
06

Évaluation et observabilité

On ne peut améliorer que ce qu'on mesure. Quand l'agent casse — et il cassera — il faut savoir exactement quel outil a été appelé, avec quels paramètres, et ce que la récupération a renvoyé.

Trace de l'exécution + tableau de métriques

Tracing complet de chaque décision. Pipelines d'évaluation avec des cas de test à réponse connue. Tests automatisés qui attrapent les régressions avant qu'elles partent en production.

Repère « Ça semble mieux » n'est pas un critère de mise en production. Les vibes, ça ne scale pas. Les métriques, oui.
07

Pensée produit

Facile à négliger parce que ce n'est pas technique — et c'est peut-être le plus important. L'agent existe pour servir des humains, avec toutes leurs attentes.

Signaler la confiance, savoir quand demander de l'aide

Quand l'agent doit-il demander une clarification ? Quand doit-il escalader vers un humain plutôt que de deviner ? C'est du design d'expérience pour un système par nature imprévisible — le même agent peut réussir une tâche un jour et la rater le lendemain.

Repère Un agent engineer pense à l'humain de l'autre côté, pas seulement au code.

Par où commencer

Pas besoin de repasser par l'école. Deux gestes suffisent pour démarrer.

1

Audite tes schémas d'outils

Relis-les à voix haute. Un nouvel ingénieur comprendrait-il exactement ce que fait chaque outil et ce qu'il attend ? Sinon, resserre : types stricts, exemples concrets. C'est le correctif à plus fort effet de levier sur la plupart des agents.

2

Débogue par la trace

Prends un échec qui te trotte en tête. Plutôt que retoucher le prompt, remonte la trace : le bon document a-t-il été récupéré ? Le bon outil sélectionné ? Le schéma était-il clair ? Neuf fois sur dix, la cause n'est pas dans les mots — elle est dans le système.
