01 Introduction & thèse centrale

Thèse Tout le monde est obsédé par le modèle d'IA, alors qu'il faudrait s'intéresser davantage au harness — tout ce qui entoure le modèle : les prompts, les skills, l'environnement de travail, et la qualité du codebase lui-même.

L'analogie utilisée est celle d'une voiture de Formule 1 : le modèle, c'est le moteur. Mais une voiture de F1, c'est aussi le châssis, l'aérodynamisme, les réglages. Le moteur n'est qu'une partie du système global, et vous avez beaucoup plus de contrôle sur le châssis (le harness) que sur le moteur (le modèle).

ModèleMoteurPuissance brute — peu de contrôle direct

02 Programmation tactique vs stratégique

En s'appuyant sur le livre A Philosophy of Software Design de John Ousterhout, on distingue deux modes de programmation.

Programmation tactique

Le travail au jour le jour :

  • Écrire du code et résoudre la syntaxe
  • Corriger des bugs mineurs
  • Créer des commits
Constat L'IA a essentiellement absorbé la programmation tactique.

Programmation stratégique

La direction globale :

  • Quelle architecture choisir ?
  • Quelles interfaces définir entre les modules ?
  • Comment rendre le codebase facile à modifier ?
Résultat Vous devez devenir excellent en stratégie pour diriger cette flotte tactique.
L'IA peut exécuter beaucoup de tâches, mais elle ne doit pas automatiquement décider de la stratégie du produit ou du système.

03 Vos compétences sont le plafond de l'IA

Principe Vos compétences agissent comme un multiplicateur pour l'IA. Si vos compétences sont faibles, l'IA ne pourra pas dépasser ce plafond.

De nombreux CTOs rapportent le même phénomène : l'IA rend les développeurs seniors dix fois plus productifs, alors qu'elle n'apporte qu'un léger boost aux juniors.

Pourquoi ? Parce qu'un développeur expérimenté possède le contexte, l'intuition architecturale, sait comment scoper proprement une tâche (délégation) et a la capacité de valider techniquement le résultat. L'IA dispose d'un contexte de travail beaucoup plus riche lorsqu'elle est guidée par un expert.

04 Les "Skills" (Procédures vs Capacités)

Dans l'écosystème agentique (comme avec Claude Code ou Fable), il existe deux grandes philosophies pour concevoir des "Skills" (compétences ou plugins) pour votre agent.

Procédures (Procedures)

Outils que l'humain invoque consciemment pour forcer l'agent à adopter un comportement spécifique.

  • Contrôle : Totalement manuel. L'humain est au volant.
  • Exemple : La skill Grill Me, qui transforme l'IA en intervieweur strict pour remettre en question vos décisions techniques avant de coder.
  • Avantage : Ne pollue pas le contexte (context window) de l'agent en arrière-plan.

Capacités (Abilities)

Outils que le modèle décide d'invoquer de lui-même de façon autonome.

  • Contrôle : Délégué à l'IA.
  • Exemple : Fournir à l'IA un document de standards de code React qu'elle lit automatiquement avant de générer un composant.
  • Inconvénient : Chaque description de capacité fuite (leak) dans le contexte, réduisant l'efficacité globale du modèle.
Best Practice Privilégiez les Procédures. Gardez le contrôle. Ne déléguez pas votre réflexion architecturale au modèle. Un bon ingénieur "bundle" ses connaissances (knowledge + skills) sous forme de procédures réutilisables pour toute son équipe.

05 Travail AFK & Modèle de Queue

Il y a une différence fondamentale entre le travail Human-in-the-loop (vous et l'agent en session interactive pour de la planification) et le travail AFK (Away From Keyboard). Découvrir le AFK est un game-changer absolu : c'est le moment où vous vous clonez.

Le mythe de la boucle infinie

Beaucoup poussent pour créer des boucles infinies (loops) où l'agent se prompt indéfiniment. Dans la réalité de l'ingénierie, une approche par Queue (File d'attente) est beaucoup plus robuste.

Issue (Ticket) ➔ Agent d'exploration ➔ Agent d'implémentation (AFK) ➔ Pull Request ➔ Revue Humaine
  • L'approche Queue : Un développeur (ou un cron job) assigne un ticket. Un agent exécute la tâche de manière isolée dans un bac à sable (sandbox) via GitHub Actions, puis crée une PR.
  • Le but de la revue humaine : Outre des raisons évidentes de sécurité, la revue de la PR n'est pas là que pour vérifier le code. Elle sert à observer comment l'agent se comporte pour améliorer le harness.

06 Produit et Vision

L'IA ne change rien aux fondamentaux de la création de produit.

Vous devez toujours parler aux clients. Vous devez toujours comprendre leurs vrais problèmes. L'IA n'inventera pas le bon produit pour vous.

En revanche, là où l'IA brille : demandez-lui "Comment puis-je simplifier cette interface ?" ou "Quelle fonctionnalité puis-je retirer pour améliorer l'UX ?". Gardez la vision produit, déléguez l'implémentation.

07 DX (Developer Experience) = AX (Agent Experience)

Si votre base de code est difficile à modifier pour un humain (mauvaise DX), elle le sera aussi pour un agent (mauvaise AX).

Optimisation du Token Spend Comment réduire vos coûts d'API (token spend) ? Ayez un codebase dans lequel il est facile de faire des changements ! Un bon codebase avec des limites claires et d'excellents tests vous permet d'utiliser un modèle "plus stupide" (et donc moins cher) pour accomplir la même tâche.

08 The Bitter Lesson

La "Bitter Lesson" en Machine Learning postule que la puissance de calcul (compute brute) finit toujours par battre les optimisations manuelles intelligentes.

Le piège : Se dire "Je ne vais pas optimiser mon harness ni mon codebase, je vais juste attendre le prochain modèle (GPT-6, Opus 5) qui sera assez intelligent pour se débrouiller."

La réponse stratégique Penser en fonction du modèle ("Model First") est une erreur. Concentrez-vous sur ce qui fonctionne depuis 30 ans : les bons principes d'architecture logicielle. Si vous construisez de bonnes fondations indépendantes du modèle aujourd'hui, vous serez le mieux placé pour exploiter la puissance brute des modèles de demain.

09 Ne corrigez pas le bug, corrigez le système

Certains s'émerveillent quand un nouvel agent IA trouve un bug de sécurité profond qu'ils n'avaient jamais remarqué. C'est bien. Mais la réaction d'un développeur x10 n'est pas de juste faire fusionner (merge) le fix.

La question stratégique est : "Pourquoi ce bug était-il là depuis si longtemps ?"

  • Manque de tests de régression ?
  • CI/CD défaillante ?
  • Besoin d'un script qui scanne automatiquement ces vulnérabilités ?

Utilisez l'IA pour corriger le bug tactique, mais utilisez votre cerveau stratégique pour construire le système (le harness) qui empêchera ce type de bug de réapparaître.

10 Plan d'Action Pratique

Étape 1 : Le grand nettoyage (Tabula Rasa)

Supprimez tous vos plugins, vos serveurs MCP, vos skills et vos instructions systèmes surchargées. Revenez à l'état brut. Observez ce que l'agent fait de base. Le contexte pollué est l'ennemi numéro un de la performance agentique.

Étape 2 : Empilez intelligemment

Ajoutez des outils uniquement sous forme de Procédures (que vous invoquez manuellement). Si vous avez besoin d'une aide à la réflexion, rajoutez le "Grill me". Ne rajoutez que ce qui résout un problème précis que vous avez identifié à l'étape 1.

Étape 3 : Déléguez AFK

Trouvez des moyens de sortir l'agent de votre terminal local pour l'exécuter dans des sandboxes distantes (via GitHub Actions, Sandcastle, etc.). Préparez le terrain, lancez l'agent et allez faire autre chose pendant qu'il prépare votre Pull Request.

Conçu pour une tâche éducative. Basé sur les principes d'AI Engineering (Matt Pocock & Huyen Chip).
