Construire un agent GraphRAG avec Neo4j et LangChain

Un RAG classique cherche des passages similaires. Un GraphRAG suit des relations. Ce cours vous montre quand choisir l'un ou l'autre, puis vous fait coder un agent Python capable de traverser un graphe de connaissances pour répondre à des questions en plusieurs étapes.

01 — Théorie

Du RAG classique au GraphRAG

Le RAG (Retrieval-Augmented Generation) part d'un principe simple : un agent reçoit une question, va chercher des informations dans une base externe, puis répond en s'appuyant sur ce contexte plutôt que sur ses seuls poids internes. C'est ce qui rend une réponse grounded, c'est-à-dire ancrée dans des faits vérifiables.

Dans un RAG classique, la base externe est le plus souvent une base vectorielle : on y cherche les passages de texte les plus proches sémantiquement de la question. Le GraphRAG remplace — ou complète — cette base par un graphe de connaissances : des entités (nœuds) reliées entre elles par des relations typées (arêtes). L'agent ne cherche plus seulement « le texte qui ressemble le plus », il peut traverser des relations explicites pour assembler une réponse en plusieurs étapes.

Règle pratique. Utilisez le RAG vectoriel pour la recherche de similarité de sens. Utilisez le GraphRAG quand la réponse dépend de relations explicites entre plusieurs entités.
02 — Cas d'usage

Quand choisir GraphRAG plutôt qu'un RAG vectoriel

Le GraphRAG a un coût : il faut modéliser les entités, maintenir le schéma, et garder le graphe à jour. Il se justifie quand les données sont riches en relations et relativement stables — pas quand elles changent en permanence ou quand une simple recherche de similarité suffit.

BesoinRAG vectorielGraphRAG

Traçabilité du chemin de réponseFaibleExcellente
Données qui changent très souventFacile à maintenirMaintenance coûteuse
Beaucoup d'entités interconnectéesMoins adaptéTrès adapté

03 — Architecture

Le pipeline GraphRAG de bout en bout

Concrètement, une question passe par une chaîne de composants avant de revenir sous forme de réponse. Le rôle central est joué par un retriever text-to-Cypher : il utilise un LLM pour traduire une question en langage naturel en une requête Cypher exécutable sur Neo4j.

L'agent

Décide s'il doit interroger le graphe, appelle l'outil, puis formule la réponse finale à partir des résultats reçus.

Le retriever

Transforme une question en langage naturel en requête Cypher, en s'appuyant sur le schéma du graphe fourni en contexte.

04 — Mise en place

Préparer l'environnement

Trois ingrédients sont nécessaires : une base Neo4j (locale, Docker, ou managée), une clé API de fournisseur de LLM, et quelques packages Python.

Fichier .env

Créez un fichier .env à la racine du projet pour stocker votre clé sans la coder en dur :

.env
OPENAI_API_KEY=votre_cle_ici

Installation des packages

bash
# avec uv
uv init
uv add "langchain[openai]" neo4j neo4j-graphrag python-dotenv

# ou avec pip
pip install "langchain[openai]" neo4j neo4j-graphrag python-dotenv

Neo4j via Docker Compose

Deux ports comptent : 7474 pour l'interface web, 7687 pour le protocole Bolt qu'utilise Python pour se connecter.

docker-compose.yaml
services:
  neo4j:
    image: neo4j:5
    ports:
      - "7474:7474"   # interface web
      - "7687:7687"   # protocole Bolt
    environment:
      - NEO4J_AUTH=neo4j/password23
bash
docker compose up -d
# interface web : http://localhost:7474
En production : utilisez un mot de passe robuste, gérez les secrets hors du code source, et limitez les permissions de l'utilisateur Neo4j.
05 — Cypher

Modéliser le graphe

Le graphe de cet exemple contient trois types de nœuds — Person, YTChannel, OS — reliés par les relations OWNS, USES et CREATED.

MERGE : chercher, sinon créer

La commande MERGE de Cypher recherche un motif existant et ne le crée que s'il est absent — l'équivalent d'un « match or create ». C'est ce qui permet de rejouer le script sans dupliquer les données.

cypher
MERGE (f:Person {name: "Florian", country: "Austria"})
MERGE (c:YTChannel {name: "NeuralNine"})
MERGE (o:OS {name: "Linux"})
MERGE (l:Person {name: "Linus Torvalds", country: "Finland"})

MERGE (f)-[:OWNS]->(c)
MERGE (f)-[:USES]->(o)
MERGE (l)-[:CREATED]->(o)

Décrire le schéma pour le LLM

Sans description du schéma, le modèle risque d'inventer des labels ou des relations qui n'existent pas dans votre base. On fournit donc un texte de contexte :

python
neo4j_schema = """
Node labels:
- Person {name, country}
- YTChannel {name}
- OS {name}

Relationships:
- (Person)-[:OWNS]->(YTChannel)
- (Person)-[:CREATED]->(OS)
- (Person)-[:USES]->(OS)
"""
06 — Implémentation

Un agent GraphRAG complet en Python

Toutes les pièces s'assemblent maintenant : connexion au driver, insertion des données, retriever text-to-Cypher, outil LangChain, puis agent.

Imports et connexion

main.py
from dotenv import load_dotenv
load_dotenv()

from langchain.agents import create_agent
from langchain.tools import tool
from neo4j import GraphDatabase
from neo4j_graphrag.llm import OpenAILLM
from neo4j_graphrag.retrievers import TextToCypherRetriever

driver = GraphDatabase.driver(
    "bolt://localhost:7687",
    auth=("neo4j", "password23"),
)

Insertion des données

main.py
driver.execute_query("""
MERGE (f:Person {name: 'Florian', country: 'Austria'})
MERGE (c:YTChannel {name: 'NeuralNine'})
MERGE (o:OS {name: 'Linux'})
MERGE (l:Person {name: 'Linus Torvalds', country: 'Finland'})
MERGE (f)-[:OWNS]->(c)
MERGE (f)-[:USES]->(o)
MERGE (l)-[:CREATED]->(o)
""")

Retriever et outil

main.py
retriever = TextToCypherRetriever(
    driver=driver,
    llm=OpenAILLM(model_name="gpt-4o-mini"),
    neo4j_schema=neo4j_schema,
)

@tool
def query_kg(question: str) -> str:
    """Interroge le graphe de connaissances.
    Peut recevoir une question utilisateur complète.
    Retourne les lignes correspondantes du graphe."""
    result = retriever.get_search_results(query_text=question)
    return "\n".join(item.content for item in result.items) or "No content"

Agent et invocation

main.py
agent = create_agent(
    model="gpt-4o-mini",
    tools=[query_kg],
    system_prompt=(
        "You are a helpful assistant with access to a knowledge graph. "
        "Query it whenever you need to."
    ),
)

if __name__ == "__main__":
    question = (
        "What country is the creator of the operating system "
        "used by the person who runs NeuralNine from?"
    )
    response = agent.invoke({"messages": [("user", question)]})
    print(response["messages"][-1].content)
    # → "Linus Torvalds, from Finland."

Observer le raisonnement avec le streaming

En passant de invoke à stream, on observe l'agent enchaîner ses appels d'outil étape par étape — utile pour déboguer ou pour auditer un comportement.

main.py
for step in agent.stream(
    {"messages": [("user", question)]},
    stream_mode="values",
):
    print(step["messages"][-1])

# Qui possède NeuralNine ?        → Florian
# Quel OS utilise Florian ?       → Linux
# Qui a créé Linux ?              → Linus Torvalds
# De quel pays vient Linus ?      → Finlande
Pour aller plus loin : avec un modèle plus capable et davantage de données, ce même pipeline répond en un seul appel à des questions à quatre ou cinq sauts — par exemple retrouver la capitale du pays de naissance de l'inventeur d'un langage de programmation enseigné sur une chaîne YouTube.

Bonnes pratiques & limites

Bonnes pratiques

Identifiants uniques et contraintes Neo4j · validation des requêtes générées · permissions restreintes · clés API hors du code · gestion explicite de l'absence de résultat.

Limites à connaître

Conception initiale plus complexe · coût de maintenance du graphe · dépendance à la qualité du schéma · risque de requêtes Cypher incorrectes générées par le modèle.
