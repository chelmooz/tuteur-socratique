Le Loop Engineering

Concevez des systèmes où l'agent IA observe, planifie, agit, vérifie, mémorise et recommence — de manière autonome, mesurable et contrôlée.

01 Introduction

Définition Le loop engineering désigne une manière de concevoir des systèmes où un agent IA ne se contente pas d'exécuter une demande ponctuelle : il peut observer, planifier, agir, vérifier, mémoriser et recommencer de manière autonome.

L'idée centrale est de placer une boucle d'exécution au-dessus des mécanismes déjà utilisés avec les agents IA. Chaque niveau répond à une limite différente :

NiveauQuestion principaleExemple
Prompt engineeringQue dois-je demander à l'IA ?« Crée une page de connexion. »
Context engineeringDe quelles informations l'IA a-t-elle besoin ?Lire le code, la documentation et la base de données.
Harness engineeringComment gérer une tâche longue ?Découper un projet en tâches persistantes.
Loop engineeringComment faire fonctionner l'agent dans la durée ?Vérifier régulièrement les erreurs, corriger et améliorer.

Le loop engineering ne remplace donc pas les autres approches. Il les superpose pour permettre à l'agent de travailler sur des tâches continues, évolutives ou récurrentes.

02 Les quatre niveaux d'ingénierie

Cliquez sur chaque niveau pour explorer son fonctionnement, ses exemples et ses limites.

01

2.1 Prompt engineering

Formuler une instruction destinée à l'agent : rôle, objectif immédiat, ton, contraintes, format attendu.

Tu es un agent de support client.
Réponds de manière polie, claire et concise.
Propose une solution concrète à chaque problème.

Efficace pour les tâches simples, lorsque toutes les informations nécessaires sont déjà disponibles dans la conversation.

Limite Un prompt seul ne permet pas nécessairement à l'agent de consulter des fichiers, interroger une base de données, utiliser une API, vérifier la réalité d'un résultat, ou maintenir un travail pendant plusieurs heures ou jours.
02

2.2 Context engineering

Permettre à l'agent de construire le contexte dont il a besoin via des outils : lecture de fichiers, recherche web, base de données, tickets, API, documents internes, connecteurs externes.

Limite Le contexte reste limité par la taille de la fenêtre, le coût des tokens, la perte d'informations lors des résumés et l'accumulation de décisions intermédiaires. Fonctionne bien pour une tâche courte ; moins fiable sur un projet complexe et long.

2.3 Harness engineering

Créer une structure externe qui pilote l'agent et gère son exécution : liste de tâches, état de progression, plans, tests, checkpoints, gestion des erreurs, reprise après interruption.

Exemple : cloner un site complexe — le harness découpe le travail en 9 étapes persistantes : analyser la structure, identifier les pages, reproduire la navigation, la page d'accueil, les composants, les données simulées, tester le responsive, corriger et vérifier.

Limite Le harness répond à la question « comment faire terminer à l'agent une tâche longue ? » mais pas à « comment faire en sorte que l'agent continue à travailler de lui-même après la fin de la tâche initiale ? ». C'est là que le loop engineering intervient.
04

2.4 Loop engineering

Ajouter une couche d'autonomie continue : l'agent s'auto-déclenche, planifie, agit, vérifie ses résultats, consigne son état et recommence sans intervention humaine constante.

Principe Le système fonctionne en permanence, s'adaptant aux retours et aux erreurs de manière autonome et mesurable.

03 Définition du loop engineering

Le loop engineering consiste à concevoir une boucle autonome qui permet à un agent de recevoir ou détecter un objectif, déterminer ce qu'il doit faire ensuite, exécuter une ou plusieurs actions, vérifier le résultat, enregistrer son état, apprendre ou améliorer ses procédures, et recommencer selon un déclencheur ou une condition d'arrêt.

Exemple

Un site web affiche les résultats d'une compétition sportive.

Sans loop engineering

Le développeur demande : « Mets à jour les scores. »

Avec loop engineering

Toutes les heures : vérifier les nouvelles données, détecter les changements, mettre à jour le site, tester, vérifier le déploiement, corriger les erreurs simples, journaliser, signaler ce qui nécessite un humain.

L'agent ne construit donc pas seulement le site. Il participe à son fonctionnement continu.

04 Les six composants du loop engineering

Six composants fondamentaux travaillent ensemble pour rendre une boucle fiable.

4.1 Automatisation

L'automatisation déclenche les boucles sans intervention humaine constante : planification horaire, événement, nouveau ticket, changement de fichier, erreur détectée, commit, webhook, seuil dépassé.

# Pseudo-configuration
name: Surveillance du site
schedule: "toutes les heures"
steps:
  - récupérer les nouvelles données
  - comparer avec l'état précédent
  - mettre à jour les fichiers concernés
  - lancer les tests
  - déployer si les tests réussissent
  - notifier en cas d'échec
Attention Une boucle permanente peut consommer beaucoup de tokens, répéter une erreur ou déclencher des actions dangereuses. Toute automatisation doit avoir une fréquence raisonnable, des limites, des conditions d'arrêt, une journalisation et des règles d'approbation humaine.

4.2 Worktrees et isolation

Lorsqu'un agent travaille sur plusieurs corrections en parallèle, les modifications peuvent entrer en conflit. Un worktree isole plusieurs versions de travail d'un même dépôt Git.

graph TD
    R["repository"] --> M["main"]
    R --> W1["worktree - bug authentification"]
    R --> W2["worktree - menu mobile"]
    R --> W3["worktree - timeout API"]

Exemple : trois bugs (authentification, menu mobile, API 500) sont confiés à trois agents dans trois worktrees indépendants — chaque modification est testée et revue avant fusion, ce qui évite la contamination entre tâches.

4.3 Skills

Une skill est une procédure réutilisable qu'un agent peut invoquer pour accomplir une tâche spécifique : description, préconditions, fichiers à consulter, étapes, commandes autorisées, critères de validation, cas d'échec.

# Skill : créer une migration de base de données

## Étapes
1. Lire le schéma actuel.
2. Vérifier les migrations existantes.
3. Produire une migration numérotée + inverse.
4. Mettre à jour les tests.
5. Exécuter dans un environnement de test.

## Interdictions
- Ne jamais supprimer une colonne sans approbation.
- Ne jamais modifier les données de production directement.
Si une tâche est réalisée plusieurs fois, elle mérite probablement de devenir une skill.

4.4 Plugins et connecteurs

Ils permettent à l'agent d'interagir avec son environnement — dépôts de code, gestion de projet, messagerie, bases SQL, monitoring, déploiement — via deux capacités essentielles :

Agir

  • Créer une branche, modifier un fichier
  • Ouvrir une pull request, créer un ticket
  • Redémarrer un service

Vérifier

  • Lire les logs, les métriques
  • Vérifier le statut du déploiement
  • Comparer deux versions

Un agent qui modifie un fichier sans pouvoir vérifier le résultat travaille en partie à l'aveugle : Action locale → Signal externe → Analyse du signal → Correction éventuelle.

4.5 Sous-agents

Les sous-agents permettent de répartir le travail entre plusieurs rôles spécialisés : recherche, implémentation, test, sécurité, revue.

    P --> C["Agent critique"]

Ils sont utiles lorsque les rôles sont clairement séparés, leurs critères d'évaluation indépendants, et le résultat vérifiable. Il faut éviter de créer des sous-agents uniquement pour multiplier les appels au modèle.

4.6 État persistant

L'état persistant permet à la boucle de savoir ce qui a déjà été fait, ce qui reste à faire, quelles erreurs ont été rencontrées, quelle version est active. Sans lui, l'agent risque de recommencer les mêmes opérations à chaque exécution.

{
  "last_run": "2026-09-13T12:00:00Z",
  "last_success": "2026-09-13T12:00:00Z",
  "version_checked": "v1.8.2",
  "pending_tasks": ["vérifier les nouveaux scores"],
  "known_issues": [],
  "attempts": 0
}

Un état utile est lisible, structuré, mis à jour après chaque étape importante, résistant aux interruptions et suffisamment détaillé pour reprendre le travail.

En pseudo-code :

while not should_stop():
    state = load_state()
    task = select_next_task(state)

    context = collect_context(task)
    plan = create_plan(task, context)

    workspace = create_isolated_workspace(task)
    result = execute(plan, workspace)

    verification = verify(result, context)

    state = update_state(state=state, task=task,
                         result=result, verification=verification)
    save_state(state)
    write_log(result, verification)

    if requires_human_approval(result, verification):
        notify_human()
        break

06 La méthode en trois couches

Pour rendre la boucle fiable : la spécification, le vérificateur, l'environnement.

Spécification
le plan de construction
Vérificateur
le poste de contrôle
Environnement

carnet & procédures

Une spécification ne doit pas seulement décrire une tâche : elle doit expliquer le but réel, le résultat attendu, les contraintes, les priorités, les critères d'acceptation, et ce que l'agent ne doit pas inventer.

Tâche Créer un rapport de fin de mois.
OBJECTIF Identifier les causes de la baisse des ventes et décider quelles actions l'équipe doit lancer le mois prochain.

Favoriser les petites spécifications

Découper une tâche importante en unités courtes, validées une à une, plutôt que de tout demander en un seul bloc.

Étape 1 : Conçois uniquement le modèle de données des projets et des tâches.
Ne crée pas encore l'interface. Présente les choix et attends validation.

Étape 2 : Implémente l'API correspondant au modèle validé.
Ajoute les tests unitaires. Ne modifie pas l'interface.

Le vérificateur définit comment déterminer si le résultat est correct — avec des critères observables, pas une déclaration vague.

Vague Le rapport doit être de bonne qualité.
PRÉCIS Trois sections, données des 6 dernières périodes, recommandation par section, faits distingués des hypothèses, source citée, aucune donnée inventée.

La vérification la plus fiable s'appuie sur des preuves externes : tests, logs, statut de déploiement, métriques, réponse réelle d'une API — jamais uniquement un code de sortie 0.

L'environnement est l'espace de travail permanent de l'agent : structure du projet, règles, skills, base de connaissances, commandes disponibles, garde-fous, conventions.

# CLAUDE.md — Instructions du projet

## Architecture
- src/    → code applicatif
- tests/  → tests
- docs/   → documentation
- scripts/→ automatisation

## Vérification obligatoire (modif. multi-fichier)
1. expliquer le plan
2. implémenter
3. lancer les tests
4. inspecter le diff
5. résumer les risques restants

08 Les garde-fous

Une boucle autonome doit distinguer trois catégories d'actions.

Toujours faire

  • Lancer les tests après modification
  • Lire le diff avant un commit
  • Mettre à jour le journal
  • Signaler les erreurs

Demander avant

  • Modifier une API publique
  • Fusionner en branche principale
  • Déployer en production
  • Supprimer une ressource cloud

Ne jamais faire

  • Exposer des secrets
  • Supprimer une base de production
  • Contourner une authentification
  • Désactiver les contrôles de sécurité

Il faut distinguer une instruction textuelle (« Ne modifie jamais /important ») d'une véritable règle technique imposée au niveau de l'outil :

PROTECTED = ["/important", "/production-secrets"]

def before_write(path):
    if any(path.startswith(folder) for folder in PROTECTED):
        raise PermissionError("Écriture interdite sur ce chemin")

Les garde-fous doivent être placés au niveau le plus bas possible :

    A["Prompt — conseil"] --> B["Règle agent — contrainte comportementale"]

09 Exemple complet : maintenance autonome d'un site

Objectif : maintenir automatiquement un site affichant les résultats d'une compétition.

    API --> U["Agent de mise à jour"]

    W --> T["Tests et validation"]
    T --> Dep["Déploiement"]

    Mon --> St["État persistant"]
    St -.-> S

1 · Déclenchement

Le scheduler lance la boucle toutes les heures.

2 · Lecture de l'état

L'agent lit le dernier match traité, le dernier déploiement, les incidents en cours.

3 · Collecte du contexte

Derniers scores, état du dépôt, incidents connus, dernier déploiement, logs récents.

4 · Décision

Deux nouveaux scores détectés, aucun incident critique → tâche créée : mettre à jour les matchs 105 et 106.

5 · Implémentation

Worktree dédié, données modifiées, tests mis à jour et exécutés, rendu vérifié.

6 · Vérification

Un sous-agent critique confirme : scores corrects, aucun historique supprimé, horaires exacts, rendu mobile fonctionnel, tests au vert.

7 · Déploiement

Commit, pull request, approbation si nécessaire, déploiement, vérification de l'URL réelle, lecture des logs.

8 · Reprise

L'état est mis à jour avec le dernier match traité, la version déployée et l'heure de la prochaine exécution.

Extrait de spécification

# Mise à jour automatique des scores

## Critères de réussite
- Toutes les données proviennent d'une source autorisée.
- Aucun match existant n'est supprimé.
- Les tests passent, le schéma JSON reste valide.
- Le déploiement est vérifié par une requête réelle.

## Demander une validation humaine si
- L'API renvoie des données contradictoires.
- Plus de 20 matchs doivent être modifiés.
- Un test critique échoue.

## Ne jamais faire
- Inventer un score manquant.
- Supprimer un résultat historique.
- Modifier directement la base de production.

10 Quand l'utiliser, et bonnes pratiques

Adapté quand la tâche est…

  • récurrente, longue, pilotée par événements
  • vérifiable automatiquement
  • composée de petites tâches successives
  • connectée à plusieurs outils

Moins adapté quand…

  • l'objectif est très subjectif
  • les critères de réussite sont inconnus
  • les actions sont irréversibles
  • la vérification automatique est impossible

Commencer petit : la montée en autonomie

ÉTAPE 1Détection → Proposition → Validation humaine
ÉTAPE 2Détection → Action limitée → Vérification → Rapport
ÉTAPE 3Détection → Action automatique → Vérification → Correction limitée

Définir une condition d'arrêt

if attempts >= 3:

if same_error_repeated >= 2:
    escalate("Erreur répétée")

if risk_level == "critical":
    require_human_approval()

Préférer les preuves aux déclarations

11 Synthèse opérationnelle

Pour construire un système de loop engineering :

  1. Définir l'objectif réel, pas seulement la tâche apparente.
  2. Transformer l'objectif en petite spécification vérifiable.
  3. Définir les critères d'acceptation avant l'exécution.
  4. Organiser l'environnement et la base de connaissances.
  5. Créer des skills pour les opérations répétitives.
  6. Ajouter connecteurs et signaux externes nécessaires.
  7. Isoler les tâches parallèles avec des worktrees.
  8. Utiliser des sous-agents aux rôles clairement séparés.
  9. Stocker l'état et le journal de chaque exécution.
  10. Ajouter limites, permissions et conditions d'arrêt.
  11. Commencer avec une validation humaine.
  12. Augmenter l'autonomie progressivement, seulement si les résultats sont fiables.
Loop engineering = automatisation + contexte + harness
+ spécification + vérification + environnement + état + garde-fous
On ne demande pas seulement à l'IA de produire une réponse. On conçoit un système dans lequel elle peut accomplir une suite d'actions, vérifier ses résultats et reprendre le travail sans perdre l'objectif.

Pour vérifier votre compréhension :

Selon vous, quelle est la différence essentielle entre le harness engineering et le loop engineering ? Écrivez votre réponse ci-dessous.

Élément clé : le harness engineering découpe et fait terminer une tâche longue (un début, une fin). Le loop engineering ajoute le déclenchement, la mémoire et la condition d'arrêt qui permettent à l'agent de continuer à travailler de lui-même après la fin de la tâche initiale — de façon récurrente, mesurable et contrôlée.
