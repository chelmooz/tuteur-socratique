ConversableAgent : faire converser plusieurs agents

Cette leçon introduit le ConversableAgent, classe d'agents intégrée à AutoGen, utilisée pour construire des conversations multi-agents. Tu apprends la fonctionnalité de base, puis tu construis ton premier chat à deux agents : la conversation amusante entre deux stand-up comedians. ⏱ 0:00

La notion d'agent dans AutoGen

Dans AutoGen, un agent est une entité qui peut agir au nom de l'intention humaine, envoyer des messages, recevoir des messages, performer des actions, générer des replies, et interagir avec d'autres agents. AutoGen fournit une classe intégrée, ConversableAgent, qui unifie différents types d'agents dans la même abstraction de programmation. ⏱ 0:27

Même interface, rôles différents

Grâce à ces capacités, tu crées des agents de rôles différents en utilisant la même interface. ⏱ 1:14

Fonctionnalités intégrées

Liste de configurations LLM pour générer des replies ; exécution de code ; exécution de fonctions et d'outils. ⏱ 0:55

Human-in-the-loop & stopping

Un composant pour garder l'humain dans la boucle et vérifier l'arrêt de la réponse. Tu allumes/éteins et personnalises chaque composant selon ton application. ⏱ 1:03

Pourquoi une seule classe ?

Unifier les agents dans la même abstraction signifie que tu n'apprends pas cinq API différentes : tu configures des composants (LLM, code exec, tools, human, stopping) à la hausse ou à la baisse. C'est ce qui rend le passage d'un agent « générique » à un agent « rôle précis » trivial — il suffit de changer le system_message. ⏱ 1:19

Premier ConversableAgent

On importe la clé OpenAI depuis l'environnement, on définit une configuration LLM (GPT-3.5 Turbo), puis on instancie un agent nommé chatbot avec human_input_mode="NEVER". ⏱ 1:24

from autogen import ConversableAgent
import os

# 1) clé depuis l'environnement (utility get_openai_api_key)
openai_api_key = os.environ.get("OPENAI_API_KEY")

# 2) configuration LLM : liste de configs
llm_config = {
    "config_list": [
        {"model": "gpt-3.5-turbo", "api_key": openai_api_key}
    ]
}

# 3) premier agent
chatbot = ConversableAgent(
    name="chatbot",
    llm_config=llm_config,
    human_input_mode="NEVER",   # ne demande jamais d'input humain
)

human_input_mode

NEVER : l'agent n'seek jamais l'input humain, il utilise seulement le LLM. ALWAYS : il demande toujours un input humain avant de générer seul. ⏱ 2:19

Config passe à l'agent

On passe la configuration définie plus haut au ConversableAgent ; l'agent peut alors utiliser ce grand modèle pour générer des replies. ⏱ 2:05

Setup minimal

Ce ne sont que les réglages de base. En général on ajoute code execution config, function execution, etc. Mais on commence simple. ⏱ 2:46

Première action : generate_reply

On appelle generate_reply avec une message list : {content: "tell me a joke", role: "user"}. L'agent répond — exemple du transcript : « Why did the scarecrow win the award? Because he was outstanding in his field. » ⏱ 2:57

Quiz express

1. human_input_mode="NEVER" signifie...

ALWAYS = demande un humain avant de générer seul.

2. generate_reply reçoit...

Exemple : {content:"tell me a joke", role:"user"}.

generate_reply ne garde PAS l'état

Point crucial du transcript : rappeler generate_reply avec « repeat the joke » ne fait PAS répéter la blague. L'appel n'altère pas l'état interne de l'agent ; c'est un appel frais, qui génère une nouvelle reply sans savoir qu'il a déjà répondu. Pour garder l'état et enchaîner des tâches, il faut une approche différente : la conversation. ⏱ 3:36

Sans état — generate_reply

Chaque appel est indépendant. Clique deux fois : tu obtiens deux replies différentes, sans mémoire.

Avec état — initiate_chat

La conversation conserve l'historique : les messages s'enchaînent et l'agent « se souvient ».

À retenir

Tu peux utiliser generate_reply sans état pour générer des replies différentes volontairement. Mais dès que tu veux maintenir l'état et faire accomplir une série de tâches, tu passes à la conversation entre agents. ⏱ 4:11

Cas pratique : deux stand-up comedians

On veut une application où deux comédiens se parlent et se moquent l'un de l'autre. Premier agent : ConversableAgent nommé Cassie, avec un system message « your name is Cassie and you are stand up comedian ». Même llm_config, même human_input_mode=NEVER. Sans system message, l'agent a un system message vide et agit comme assistant générique. ⏱ 4:33 

cassie = ConversableAgent(
    name="Cassie",
    system_message="Your name is Cassie and you are a stand-up comedian.",
    llm_config=llm_config, human_input_mode="NEVER",
)

joe = ConversableAgent(
    name="Joe",
    system_message="Your name is Joe and you are a stand-up comedian. "
                   "Start the next joke from the punch line of the previous joke.",
    llm_config=llm_config, human_input_mode="NEVER",
)

# Joe initie la conversation
result = joe.initiate_chat(
    recipient=cassie,
    message="I'm Joe. Cassie, let's keep the jokes rolling.",
    max_turns=2,
)

system_message

Il personnalise le comportement de l'agent. Ici il donne le rôle (comédien) et une instruction de continuité (démarrer la blague suivante depuis la punchline précédente). ⏱ 4:48

Instruction de carry-over

« start the next joke from the punch line of the previous joke » : c'est ce qui rend l'échange cohérent et drôle. ⏱ 5:25

initiate_chat

On l'appelle depuis un agent (Joe), recipient = Cassie, message initial donné, max_turns = 2 → deux tours puis fin. ⏱ 5:42

Clique « Message suivant » pour dérouler l'échange Joe ↔ Cassie (max_turns=2).

is_termination_msg : un arrêt plus flexible

Et si tu ne connais pas le bon nombre de tours à l'avance ? On change la condition de terminaison via une configuration is_termination_msg : une fonction booléenne qui prend un message et retourne true/false (faut-il arrêter ?). On passe le message « when you're ready to end the conversation say I got go », et la condition vérifie si « I got go » est dans le message. Chaque agent vérifie la condition sur le message reçu de l'autre ; s'il voit « I got go », il arrête de répondre. ⏱ 9:16 

def is_termination_msg(msg):
    return "I got go" in msg.get("content", "")

cassie = ConversableAgent(..., is_termination_msg=is_termination_msg)
joe    = ConversableAgent(..., is_termination_msg=is_termination_msg)
# instruction ajoutée : "when you're ready to end the conversation say I got go"

Playground : évalue la condition d'arrêt

Résultat observé

Avec cette condition, la conversation a plus de tours ; le dernier message de Joe est « Glad you enjoyed it Cassie. Puns are always a hit. Thanks for the laughs. I got go. » Cassie le voit en premier et arrête de répondre. ⏱ 10:34

Plus flexible que max_turns

max_turns impose un nombre fixe ; is_termination_msg laisse les agents décider quand finir, selon un signal dans le contenu. ⏱ 11:13

Appliqué aux deux agents

La condition est donnée à chaque agent : chacun vérifie le message reçu de l'autre avant de répondre. ⏱ 10:09

Quiz express

1. is_termination_msg est...

Retourne true si le message signifie qu'il faut terminer.

2. Qui arrête de répondre quand « I got go » apparaît ?

Chaque agent vérifie la condition sur le message reçu de l'autre.

Continuer la conversation & préserver l'état

Après la fin, veut-on continuer et vérifier que l'agent préserve l'état ? On teste : Cassie envoie un nouveau message à Joe, « What's the last joke we talked about? ». Bingo : Joe se souvient — la dernière blague était l'épouvantail primé parce qu'il était « outstanding in his field ». La même condition de terminaison s'applique : Cassie dit « I got go », Joe arrête de répondre. ⏱ 11:17 

# continuer : Cassie -> Joe, même condition d'arrêt
result2 = cassie.initiate_chat(
    recipient=joe,
    message="What's the last joke we talked about?",
    max_turns=2,  # ou is_termination_msg partagé
)
# Joe se souvient de la blague précédente (état préservé)

Démonstration clé

Cela montre comment mélanger le travail des agents en conversation : démarrer, continuer, se souvenir de ce qu'ils ont fait. ⏱ 12:09

Condition partagée

Ils suivent la même termination condition ; le signal « I got go » circule dans les deux sens. ⏱ 12:02

Extension : faire tourner les agents en local (Ollama)

Le transcript AutoGen utilise OpenAI (GPT-3.5 Turbo). Pour éviter les coûts d'API et garder tes données chez toi, tu peux brancher un modèle local compatible OpenAI via Ollama. Cette partie est une extension issue de ta base de connaissances (mini-cours Ollama), pas du transcript AutoGen lui-même — mais le principe est identique : on remplace la config_list par une base URL locale. 

# Ollama tourne un serveur compatible OpenAI sur localhost:11434
# AutoGen : même abstraction ConversableAgent, autre config LLM
llm_config = {
    "config_list": [
        {
            "model": "llama3.2",                 # modèle local Ollama
            "base_url": "http://localhost:11434/v1",
            "api_key": "ollama",                 # non requis mais à passer
        }
    ]
}
# Le reste (ConversableAgent, initiate_chat, is_termination_msg...) est inchangé.

Pourquoi ça marche

Ollama expose une API REST compatible OpenAI (endpoint /v1) ; AutoGen, qui parle OpenAI, n'a qu'à changer la base URL et la clé. Base Ollama ⏱ 1:00:55

Avantages

Gratuit, privé (données non envoyées à un serveur externe), latence réduite, et tu peux tester tes agents avant la prod. Base Ollama ⏱ 10:22

Trade-off

Un petit modèle local (ex. llama3.2 3B) sera moins fiable qu'un grand modèle cloud pour le raisonnement multi-étapes. Teste et choisis le modèle qui convient à ta tâche.

Pont avec la base de connaissances

Le mini-cours Ollama construit justement une « AI Recruiter Agency » avec le framework Swarm (agents qui se délèguent des tâches) en local via llama3.2 — un cousin direct des conversations multi-agents AutoGen. Les mêmes idées (orchestrateur, agents spécialisés, délégation) s'y retrouvent. Base Ollama ⏱ 28:44

Patterns & anti-patterns

Ce que la leçon annonce pour la suite, et les pièges classiques du multi-agent chat.

À venir (transcript)

Tool using, reflection, planning, code execution, etc. — d'autres patterns de conversation et de design d'agents. ⏱ 12:28

Pattern : rôle via system_message

Un seul ConversableAgent, des rôles différents obtenus juste en changeant le system_message (et ses instructions de carry-over).

Pattern : arrêt sémantique

is_termination_msg pour finir sur un signal de contenu (« I got go ») plutôt qu'un nombre arbitraire de tours.

Anti-patterns

Confondre generate_reply et conversation

Vouloir « répéter » via generate_reply isolé : pas d'état, donc pas de mémoire. Utilise initiate_chat pour enchaîner.

max_turns trop grand « au cas où »

Coût et latence inutiles. Préfère une condition d'arrêt sémantique quand le nombre de tours est inconnu.

Oublier la condition des deux côtés

is_termination_msg doit être donnée à chaque agent, sinon l'un des deux continue indéfiniment.

summary=LAST pris pour un résumé

Le dernier message n'est pas une synthèse. Utilise REFLECTION + prompt pour un vrai résumé.

human_input_mode mal calibré

NEVER partout = aucune supervision ; ALWAYS partout = friction. Choisis selon le risque de l'action.

Scénarios : quel réglage pour quel besoin ?
