Les fondamentaux du logiciel comptent plus que jamais

Message réconfortant pour ceux qui craignent que leurs compétences ne valent plus rien : les fondamentaux du logiciel comptent davantage que jamais. Ce cours décortique le mythe du specs-to-code, les cinq failure modes du codage avec IA, et les cinq skills qui les corrigent — grill-me, ubiquitous language, TDD, improve-codebase-architecture, write-PRD — tous ressuscités de vieux livres : Ousterhout, The Pragmatic Programmer, Frederick P. Brooks, le DDD, Kent Beck. ⏱ 0:22

Thèse

Le code n'est pas cheap : le mauvais code n'a jamais été aussi cher, car un codebase difficile à changer t'empêche de récolter les bénéfices de l'IA. ⏱ 3:55

Méthode

Chaque failure mode du codage IA se corrige avec un concept classique + un skill réutilisable : concept de design, langage ubiquitaire, feedback loops, modules profonds, programmation stratégique.

Cas pratique

Un builder applique la stack complète (grill-me → ubiq. language → PRD → TDD → architecture → revue stratégique) sur une feature, avec console et code de référence.

Diagnostic initial

Trois questions pour adapter ton parcours.

Le mythe du specs-to-code

Le mouvement specs-to-code promet : écris une spécification, l'IA la transforme en code ; si ça ne va pas, modifie la spec — jamais le code — et relance le compilateur. ⏱ 1:08

Ce que j'observe

Premier run : du code. Deuxième : du pire code. Troisième : encore pire. À force de relancer le compilateur sans regarder le code… du garbage. ⏱ 1:42

Verdict

« Ignorer le code et le laisser se gérer seul » n'est que du vibe coding sous un autre nom. La vraie question n'est pas « comment réparer le compilateur » mais « comment expliquer à un LLM, en anglais, à quoi ressemble un bon codebase ». ⏱ 2:12

Cas pratique 1 — Le compilateur à entropie

Relance le compilateur depuis la spec, avec ou sans investissement de design à chaque passe. Observe la qualité du codebase : c'est l'entropie logicielle en direct.

Qualité du codebase : 70 % (code initial généré)

Sans investissement de design, chaque passe ajoute du code qui ne pense qu'à son changement : le système dérive vers le désastre.

Quiz express

1. En specs-to-code pur, relancer le compilateur produit…

C'est l'entropie : chaque passe qui ne pense qu'à son changement dégrade le tout. ⏱ 1:42

2. « Ignorer le code et le laisser se gérer » équivaut à…

Le code reste l'actif central : c'est lui qu'il faut garder compréhensible. ⏱ 2:12

Complexité, entropie, et le vrai coût du code

Complexité (Ousterhout)

« Tout ce qui, dans la structure d'un système logiciel, le rend difficile à comprendre et à modifier. » Un mauvais codebase = un codebase difficile à changer ; un bon = facile à changer. ⏱ 2:36

Entropie (Pragmatic Programmer)

Les systèmes tendent vers le désastre. Chaque changement pensé isolément, sans le design du système entier, fait empirer le codebase — exactement ce que produit le specs-to-code. ⏱ 3:11

« Code is cheap » : faux

Le mauvais code n'a jamais été aussi cher : un codebase dur à changer t'empêche de récolter les bénéfices de l'IA… alors que l'IA excelle sur un bon codebase. ⏱ 3:55

Thèse

Les bons codebases comptent plus que jamais → les fondamentaux du logiciel comptent plus que jamais. ⏱ 4:20

Corollaire pratique

Avant d'accuser l'IA, mesure la facilité de changement de ton codebase : c'est le plafond de tout ce que l'IA pourra y produire de bon.

Quiz express

1. Un bon codebase, c'est un codebase…

Définition opérationnelle d'Ousterhout : la modifiabilité. ⏱ 2:55

2. Pourquoi le mauvais code est-il « le plus cher de tous les temps » ?

L'IA performe très bien sur un bon codebase ; un mauvais codebase annule ce levier. ⏱ 4:02

Failure mode 1 : « l'IA n'a pas fait ce que je voulais »

Personne ne sait exactement ce qu'il veut — ni toi, ni l'IA : il y a une barrière de communication. Parler à l'IA, c'est sa phase de recueil de besoin. ⏱ 4:51

Design concept (Brooks)

Quand plusieurs personnes conçoivent ensemble, une idée éphémère flotte entre elles : la théorie invisible de ce qu'on construit. Ce n'est pas un asset, pas un fichier markdown. ⏱ 5:15

Skill : grill-me

« Interviewe-moi implacablement sur chaque aspect de ce plan jusqu'à ce qu'on atteigne une compréhension partagée. Descends chaque branche de l'arbre de design, en résolvant les dépendances une par une. » ~13 000 stars : viral. ⏱ 5:44

Effet

40, 60, parfois 100 questions avant satisfaction. L'IA devient un adversaire qui ping des idées ; la conversation générée devient un PRD — ou directement des issues pour ton agent AFK. ⏱ 6:17

vs plan mode

Le plan mode de Claude Code est trop pressé de créer un asset : il veut produire un plan et démarrer. Atteindre d'abord un design concept partagé est plus sain. ⏱ 6:53

Quiz express

1. Le design concept, c'est…

C'est la théorie flottante entre concepteurs ; l'aligner précède tout artifact. ⏱ 5:24

2. grill-me transforme l'IA en…

Des dizaines de questions, branches descendues une par une. ⏱ 6:29

Failure mode 2 : « l'IA est beaucoup trop verbeuse »

Vous parlez presque à contre-sens. Comme avec un expert du domaine (ex. microchips) : sans langage partagé, chacun traduit dans son propre jargon et le code final ne reflète ni l'un ni l'autre. ⏱ 7:26

Langage ubiquitaire (DDD)

Conversations entre devs, expressions du code et échanges avec l'expert dérivent du même modèle du domaine. Concrètement : un markdown de termes alignés, utilisés partout. ⏱ 8:16

Skill : ubiquitous-language

Scanne le codebase, extrait la terminologie, produit un markdown de tables de termes. Tu le lis, tu le gardes ouvert pendant le grilling et le planning. ⏱ 9:02

Effet observé

Dans les thinking traces : planification améliorée, pensée moins verbeuse, implémentation alignée avec le plan. « Un powerhouse. » ⏱ 9:19

Failure mode 3 : « c'est la bonne chose, mais ça ne marche pas »

Feedback loops

Types statiques (TypeScript, sinon « c'est fou »), accès au navigateur pour le front-end, tests automatisés. ⏱ 9:58

Le LLM les utilise mal

Il fait trop à la fois : énormément de code, puis « ah, je devrais peut-être type-checker ». ⏱ 10:23

Outrunning your headlights

Pragmatic Programmer : la vitesse de feedback est ta limite de vitesse. Tester en avançant, petits pas délibérés. ⏱ 10:48

Skill : TDD

Test d'abord → le faire passer → refactorer en pensant au design. Le TDD force l'IA aux petits pas. ⏱ 11:12

Tester reste difficile : taille de l'unité, quoi mocker, quels comportements tester — décisions interdépendantes. Mais un bon codebase est un codebase facile à tester : meilleur codebase → meilleurs feedback loops → meilleur code de l'IA. ⏱ 11:32

Règle : taille du pas ≤ vitesse de feedback. Active le mode TDD pour forcer les petits pas et compare bugs livrés vs features livrées.

Ne pas dépasser ses phares : le feedback borne la taille des pas. ⏱ 10:56

Failure mode 4 : le codebase que l'IA ne comprend pas

Module profond (Ousterhout)

Beaucoup de fonctionnalité cachée derrière une interface simple. Tu peux regarder dedans, mais tu n'as pas besoin : l'interface suffit. ⏱ 12:46

Module shallow

Peu de fonctionnalité, interface complexe. Un codebase plein de shallow modules = une nuée de petits blobs que l'IA doit traverser : elle explore mal, ne comprend pas, rate les dépendances. ⏱ 13:07

Codebase à modules profonds

Même code, mais structuré en frontières avec interfaces soignées au sommet. L'interface : tu la conçois. L'implémentation : tu peux la laisser à l'IA. ⏱ 13:58

Skill : improve-codebase-architecture

Explorer le codebase, repérer le code relié, l'enrouler dans un module profond. Testable : on teste à l'interface. Un codebase qui récompense le TDD. ⏱ 14:21

Cas pratique 5 — Shallow → profond

Visualise la même fonctionnalité en blobs shallow (spaghetti) puis refactorée en modules profonds (frontières + interfaces). Mesure la charge d'exploration.

Quiz express

1. Un module profond, c'est…

La complexité est cachée ; l'interface suffit à l'usage. ⏱ 12:59

2. Pourquoi les modules profonds aident-ils l'IA ?

On teste à l'interface ; l'implémentation peut être déléguée. ⏱ 14:50

Failure mode 5 : ton cerveau ne suit plus

Tu ships plus de code que jamais, mais plus fatigué que jamais : toi comme l'IA devez garder tout cela en tête. Les modules profonds deviennent des boîtes grises : tu conçois l'interface, tu ne revues pas trop l'implémentation (sauf critique, ex. finance), tu vérifies par les tests depuis l'extérieur. ⏱ 15:04

Tip 5

Conçois l'interface, délègue l'implémentation. Cela sauve le cerveau : le module est vérifié de l'extérieur. ⏱ 16:16

Carte des modules

La carte des modules fait partie du langage ubiquitaire et du planning : le skill write-PRD précise les modules touchés et comment leurs interfaces changent. ⏱ 16:27

Kent Beck

« Investis chaque jour dans le design du système. » Le specs-to-code ne fait pas cela : il désinvestit du design. ⏱ 16:52

Stratège vs tacticien

L'IA = excellent programmeur au sol, tacticien, sergent qui fait les changements. Au-dessus, il faut un stratège : toi. Cela exige les fondamentaux du logiciel. ⏱ 17:23

Message final

Le code n'est pas cheap. Le code est important. ⏱ 17:16

Quiz express

1. Traiter un module non critique en « boîte grise » signifie…

L'implémentation est déléguée ; la frontière reste sous contrôle. ⏱ 15:42

2. Dans la métaphore militaire, l'IA est…

Et toi, le niveau stratégique : design, interfaces, carte des modules. ⏱ 17:23

Anti-patterns du codage avec IA

      

        
Relancer le compilateur sans lire le code
Entropie garantie : chaque passe empire la précédente jusqu'au garbage.

        
Plan mode pressé
Créer un asset-plan avant d'avoir un design concept partagé : l'IA part confiante dans la mauvaise direction.

        
Énorme PR puis type-check
Outrunning your headlights : le feedback arrive trop tard pour borner le pas.

        
Prolifération de modules shallow
L'IA adore en créer : spaghetti inexplorable, compréhension impossible, tests impossibles.

        
Zéro types, zéro tests, zéro navigateur
Agent aveugle et sourd : aucune boucle de feedback, donc aucune limite de vitesse.

        
Tout revoir en détail
Sans boîtes grises, le cerveau sature : réserve la revue d'implémentation aux modules critiques.

        
Jargon non aligné
Sans langage ubiquitaire : verbosité, contresens, implémentation décalée du plan.
