Agent Skills : encoder les réflexes d'un ingénieur senior dans vos agents IA

Le dépôt addyosmani/agent-skills fournit des production-grade engineering skills pour agents de codage IA. L'idée : les agents par défaut prennent souvent le chemin le plus court — ils sautent les specs, les tests, la sécurité, la revue, le déploiement progressif. Ce pack encode les workflows, quality gates et bonnes pratiques que les ingénieurs seniors utilisent, via 9 slash commands, 25 skills, des personas spécialisés et des références partageables.

Objectif

Comprendre comment transformer un agent de codage IA en exécutant discipliné : spec avant code, petits pas, tests comme preuve, revue avant merge, ship plus sûr.

Méthode

Processus, pas prose ; anti-rationalisation ; vérification non négociable ; progressive disclosure ; skills activés automatiquement selon la tâche.

Cas pratique

Construire un workflow complet sur une feature réelle, avec /build guidé ou /build auto, puis générer un SKILL.md personnalisé.

1. Pourquoi Agent Skills ?

Les agents IA de codage ont un défaut structural : ils cherchent le chemin le plus court. Résultat : ils sautent les specs, les tests, la sécurité, la revue et les garde-fous de déploiement. Agent Skills leur donne des workflows structurés qui imposent la même discipline qu'un ingénieur senior en production.

Problème

« I'll add tests later » / « The code seems right » / « Let's ship quickly » : ces rationalisations produisent du prototype, pas de la production.

Réponse

Chaque skill est un processus avec étapes, checkpoints, critères de sortie, tableaux d'anti-rationalisation et exigences de preuve.

Philosophie

Process, not prose. Les skills ne sont pas des docs à lire : ce sont des workflows que l'agent suit.

Vérification

« Seems right » n'est jamais suffisant. Chaque skill se termine par des preuves : tests passants, build output, runtime data.

2. Cycle de vie & slash commands

      

        Le pack expose 9 slash commands qui mappent au cycle de vie de développement. Chaque commande active automatiquement
        les bons skills. L'objectif : rendre explicite ce qui, sinon, serait oublié sous pression de vitesse.
      


      

        
/spec
Spec before code. Écrire un PRD : objectifs, commandes, structure, style, tests, boundaries.

        
/plan
Small, atomic tasks. Décomposer la spec en tâches vérifiables avec critères d'acceptation et dépendances.

        
/build
One slice at a time. Implémentation incrémentale : tranches verticales fines, testées, committées.

        
/test
Tests are proof. Red-Green-Refactor, test pyramid, DAMP over DRY, Beyoncé Rule.

        
/constraints
Decide it once, enforce it everywhere. Écrire CONSTRAINTS.md : seuils qualité, checks, garde-fous.

        
/review
Improve code health. Revue five-axis, change sizing ~100 lignes, sévérités Nit/Optional/FYI.

        
/webperf
Measure before you optimize. Audit Core Web Vitals, modes Quick/Deep, metric-honesty rule.

        
/code-simplify
Clarity over cleverness. Chesterton's Fence, Rule of 500, réduire la complexité sans casser le comportement.

        
/ship
Faster is safer. Feature flags, staged rollouts, rollback, monitoring, checklists pré-launch.

/build auto
Si la spec existe, /build auto génère le plan et implémente toutes les tâches en une passe approuvée. Il supprime l'intervention humaine entre les tâches, mais pas la vérification : chaque tâche reste test-driven, committée individuellement, et le processus pause sur échec ou étape risquée.
